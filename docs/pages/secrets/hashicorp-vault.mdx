# Use HashiCorp Vault

Use Vault when you already run one, or want credentials to live in a
self-hosted KV store. As with every backend, sandboxes receive placeholders
and [iron-proxy](https://docs.iron.sh) resolves the real value at the network
boundary.

Vault is a **per-secret** backend: you pick `HashiCorp Vault (KV)` on each
secret in the Console. It is independent of `ironProxy.secretSource`, which
only governs secrets declared by placeholder alone with no Console record.

The `vault_kv` source requires iron-proxy `0.50.0` or later.

**Scope.** This source covers static KV v1 and v2 secrets only. Vault dynamic
engines (lease-based credentials that Vault rotates) are not resolved directly.
Run a [Vault Agent](https://developer.hashicorp.com/vault/docs/agent) or
Secrets-Manager-Cache sidecar and point the `file` source at what it writes if
you need rotating credentials.

## Authenticate

iron-proxy uses the official Vault API client, so it reads the standard
`VAULT_*` environment variables. Every key in the infra Secret is projected
into each iron-proxy pod, so set them there:

```text
VAULT_ADDR
VAULT_TOKEN
VAULT_NAMESPACE   # Vault Enterprise only; omit on OSS
```

Local bootstrap adds these when present in your shell:

```bash
VAULT_ADDR=https://vault.example.com:8200 \
VAULT_TOKEN=... \
VAULT_NAMESPACE=... \
contrib/scripts/bootstrap-k8s-secrets.sh
```

For production, prefer a short-lived token from a Vault Agent sidecar over a
static `VAULT_TOKEN`, and note that file-based TLS variables (`VAULT_CACERT`,
`VAULT_CLIENT_CERT`, `VAULT_CLIENT_KEY`) must point at files that exist inside
the proxy pod.

## Create the secret

In the Console, add a secret and set **Backend** to `HashiCorp Vault (KV)`. The
form takes two fields:

| Field | Meaning |
|-------|---------|
| **Mount** | KV mount holding the secret, e.g. `secret` |
| **Secret path** | Path within the mount, e.g. `prod/app/api-key` |

Together they address `secret/prod/app/api-key`. The mount defaults to nothing,
so it is required.

The same thing over the JSON API:

```json
{
  "source_type": "vault_kv",
  "config": { "mount": "secret", "path": "prod/app/api-key" }
}
```

### Picking one field

A Vault KV entry is a JSON object, not a single string. iron-proxy resolves the
**whole entry**, so set a **JSON key** to select the field you actually want.
With `{ "credential": "s3cr3t" }` stored at that path, add `"json_key":
"credential"` — otherwise the injected value is the entire JSON document rather
than the credential.

Use `kv_version: 1` only for a KV v1 mount; it defaults to `2`.

## Network reachability

iron-proxy pods already allow egress on 443 to public addresses, so a Vault
server on a routable address needs no extra chart wiring. A Vault reachable only
at a private or in-cluster address needs an explicit egress rule, mirroring the
1Password Connect policy in `contrib/chart/templates/networkpolicy.yaml`.

## Verify

Confirm the proxy received the Vault configuration:

```bash
kubectl exec -n centaur-system deploy/centaur-centaur-api-rs -- env | grep VAULT_
```

Then create the secret and confirm the proxy reports the source:

```bash
kubectl logs -n centaur-system -l centaur.ai/iron-proxy=true | grep -i vault
```

If injection fails, check in this order: the `VAULT_ADDR`/`VAULT_TOKEN` the pod
actually has, that the mount and path address a real KV entry, whether the
mount is v1 or v2, and whether you set a JSON key when the entry is an object
rather than a string.
