Why the earlier plans were wrong, and what changed in method

Versions 1 and 2 were built from search results, launch coverage, and inference. Six material claims turned out to be wrong — the licence, the Teams adapter, the web console, the control-plane language, the credential model, and the secrets backend. Every correction came from reading the actual repository.

This version reads the source first. Each claim is marked:

Source verified in the repository code or chart  ·  Docs stated in official documentation, not yet executed  ·  Unknown must be tested

Nothing marked Docs or Unknown should be treated as a commitment. Phase 0 exists to convert them.

01The finding that governs everything

🔴 Centaur's own documentation contradicts itself on per-user credentials

The security page says it does not work. Under "What this does not protect against": credentials are deployment-scoped, not yet user-scoped. Tool and harness secrets live in a single vault every sandbox draws from, so a tool's reach is the same regardless of which user invokes it. Per-user and per-channel scoping is described as on the roadmap.

The permissions page says it does work. A page titled "Per-User Permissions" documents principals, roles, direct grants, and effective grants — with console UI paths and working centaur-perms CLI commands for grant, show, and revoke. It calls per-user permissions "the normal production model for shared workspaces."

The code sides with the permissions page. Source The centaur-perms crate exists with a principal model and tests. The console has OauthApp and BrokerCredential models with per-user consent flows. Teams principals derive from tenant and user IDs.

Most likely explanation: the security page is stale and was not updated when the feature shipped. But "most likely" is exactly the reasoning that produced three wrong plans.

Resolution: test it, do not read more about it. This is the first task of Phase 0 and the whole project turns on it.

What this does to the plan

Phase 1 in v2 was "the decisive phase, our largest build item." It is now two OAuth strategy classes of roughly fifty to ninety lines each, following a documented extension pattern, plus tests. That is days of work, not months — if the contradiction in section 01 resolves in our favour.

The real remaining work moved to the tools and the knowledge base. Those are ours to write regardless of platform, and they are portable by construction.

🟡 Two security defaults to change immediately

The egress allowlist ships permissive on purpose — a deliberate usability choice, with the docs advising that maximal security means locking it down up front. We lock it down before any real credential is registered.

Containment is at the sandbox boundary, not inside it. Agents can read and write the sandbox filesystem, run shell commands, and call any tool their token allows. Tool design for destructive operations must assume the agent will sometimes do the wrong thing. That is an argument for write-approval gates in our layer, not a reason to hesitate.

Chart resource limits are unset by default Source — the chart ships resources: {} for most services. There are no published minimums. Sizing must be measured during Phase 0, not estimated. That is why no cloud SKU table appears in this document.

04Portability doctrine

Standing test: if we replaced Centaur tomorrow, what would we rewrite? The acceptable answer is "the adapter and two OAuth strategies."

┌──────────────────────────────────────────────────────────────────────┐
│  OURS — portable, zero Centaur imports                               │
│  Spaces layer · Knowledge base · Audit ledger · Budgets              │
│  Tools (plain HTTP, REST contract)                                   │
└─────────────────────────────┬────────────────────────────────────────┘
                              │  our interface
┌─────────────────────────────▼────────────────────────────────────────┐
│  ADAPTER — the only code that knows Centaur exists                   │
│  spawn → message → execute · durable events · principal grants       │
└─────────────────────────────┬────────────────────────────────────────┘
                              │
┌─────────────────────────────▼────────────────────────────────────────┐
│  CENTAUR — pinned. Two added files (OAuth strategies), else untouched│
└──────────────────────────────────────────────────────────────────────┘
  1. Never modify kernel files. The OAuth providers are the single exception, and they are new files plus one registry line — the cheapest possible divergence.
  2. Upstream the providers. HubSpot and Microsoft are broadly useful. Offer them to Paradigm. If accepted, our divergence returns to zero.
  3. Our own schema. Knowledge base, audit ledger, space definitions in a magik schema with its own migrations.
  4. No foreign keys into their tables. Opaque IDs only.
  5. Tools stay plain HTTP. The REST contract makes them portable to any runtime. No Centaur SDK in tool code.
  6. One import boundary, enforced in CI. Nothing outside the adapter may import Centaur packages. A violation fails the build.
  7. Audit written by us at the decision point, never derived from their event stream.
  8. Pin upstream by commit and digest. Scheduled merges, full test run before landing.
  9. Write the escape hatch on day one — what any replacement runtime must provide.
  10. Track three metrics: adapter size, time-to-merge on upstream sync, import-boundary violations. Plus a quarterly one-page replacement drill.

Abandonment is already survivable

Dual Apache-2.0 / MIT means the code cannot be withdrawn. If Paradigm stops maintaining Centaur or takes it somewhere we dislike, we pin to the last good commit and self-maintain at our own pace. The risk is cost, never a forced march.

05Phases

Local through Phase 4. Azure only when the whole company adopts it. Every phase has an exit condition; the first two have kill conditions.

Phase 0

Resolve the contradiction

1–2 weeks, part time · local
  • Provision the host. Install k3s and tooling. Clone, just up, just smoke until PONG returns.
  • Test per-user credential isolation directly. Two principals, two secrets, grant each to one principal only. Confirm principal A's session cannot resolve principal B's secret. This settles section 01.
  • Exercise the console: Principals, Roles, Direct Grants, Effective Grants, OAuth Apps.
  • Measure the real resource footprint of control plane, console, Postgres, and one sandbox.
  • Assess console coverage against our web and profile requirements.
  • Lock down the egress allowlist. Confirm default-deny behaves as documented.
  • Write the escape-hatch document.
Exit: isolation proven or disproven with evidence; footprint measured; console coverage assessed.
Kill: the security page is right and per-user scoping genuinely does not exist. Stop and reassess platform choice before writing any of our code.
Phase 1

Our identities, our tools

local
  • HubSpot OAuth strategy class + registry entry + tests. Offer upstream.
  • Microsoft OAuth strategy for Graph. Same pattern.
  • HubSpot tool and Microsoft 365 tool — or evaluate Composio as a shortcut first.
  • Teams bot against our tenant, through a tunnel. Confirm AAD principal derivation.
  • Import-boundary CI rule active from the first commit.
Exit: two real staff members connect their own HubSpot accounts by consent link, and each agent session acts as the correct person with the correct permissions.
Kill: per-user identity cannot be preserved end to end. Do not proceed to real client data.
Phase 2

The knowledge base

local · our highest-value asset
  • SharePoint ingestion, chunking, embedding, source and owner metadata.
  • Mandatory citation on every answer. Staleness flagged in-response, never served silently.
  • Named curator and review cadence per collection.
  • Spaces layer: definitions, prompts, tool grants, knowledge scoping, write-approval gates.
  • Audit ledger and per-space budgets.
Exit: a document produced in a space cites current, correct company sources, and every write is logged and approved.
Phase 3

Sales Scout, small group

local · real work, limited blast radius
  • Two or three volunteers from sales. Real HubSpot, real email.
  • Measure time saved. Collect what breaks.
  • Backups and a documented rebuild path for the host — it now holds real tokens.
Exit: measured time saved justifies continuing. If not, we learned it for the cost of one machine.
Phase 4

More spaces, still local

local
  • Add spaces in the order the team asks for them.
  • Watch for the ceiling: concurrency limits, single-host availability, patch windows people notice.
Exit — the Azure trigger: the platform is depended on daily, the host cannot carry concurrent load, or an outage genuinely hurts. Not a date. A symptom.
Phase 5

Azure, company-wide

when Phase 4 exits
  • Activate ISV credits then — the 12-month clock starts on activation, and every idle month is waste.
  • AKS with the sandbox pool on separate nodes from the control plane, sized from Phase 0 measurements.
  • Managed Postgres with HA and geo-redundant backup, Canada Central.
  • Entra SSO, WAF ingress, NAT egress with a static IP, private endpoints.
  • Secrets: 1Password Connect carried forward, or an Azure provider written by then.
  • Paid subscription for production — credits can be revoked when programme membership changes.

07Open questions

  • The contradiction in section 01. Everything depends on it. First task, before any of our code.
  • ISV credit terms. Programme is aimed at ISVs publishing to Marketplace; we are building internal tooling. Confirm eligibility for our use before relying on it in Phase 5.
  • Composio versus native tools. May remove two build items or add a dependency. Evaluate in Phase 1 before writing anything.
  • Console coverage. Determines whether we build a web surface at all.
  • Named owner. Still unassigned. Required before Phase 0 starts.

What this asks for

One always-on x86 Linux machine, a 1Password service account, an OpenAI key, and a named owner.

No cloud spend. No credit clock. No commitment beyond the first two weeks — which exist to answer one question the documentation cannot answer for us: whether Centaur can hold our team's identities separately. Everything else in this plan waits on that.
